# Explainability contract

Each recommendation is generated from a solved, independently validated run and contains: asset, action, start/end, kW and kWh, comparator baseline, predicted change in named metrics, assumptions and provenance, active constraints, tested reliability or `unknown`, solver status, and run ID. A recommendation with unmet critical service, failed balance, or no feasible incumbent is suppressed.

Example structured explanation: “Schedule 18 kW of EV charging at 13:00–14:00 instead of 18:00–19:00. In this **simulation**, the central forecast has solar surplus and the selected tariff has a higher evening price. The battery reserve limit prevents more shifting. Across the documented stress set, required EV energy is met in 8/10 cases; this is not a field reliability estimate.” All numbers must be computed from two schedule traces and their assumptions, not generated by a language model.

Explain binding constraints carefully: use verified slack (`bound−value`) and counterfactual reruns where necessary; do not assert economic causality solely from a dual value in a MILP. Templates can verbalize structured facts. An optional LLM can paraphrase only a signed JSON result and must be checked against it; it is unnecessary for MVP. Show why no action is recommended (poor data, infeasibility, no benefit, or unreliable response). User can inspect the interval plot and source fields behind each claim.
